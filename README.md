# Бронювання переговорних

Вебзастосунок для бронювання переговорних кімнат в офісі, створений у межах конкурсу **UA-Skills**. Користувач може переглядати тижневий розклад кімнат, бачити зайняті слоти, створювати власні бронювання, редагувати їх назву, скасовувати майбутні бронювання та переглядати історію на сторінці **My bookings**.

## Демо

- Frontend: https://meeting-room-booking-ruby.vercel.app/
- Backend API: https://meeting-room-booking-backend-1ejl.onrender.com/api

> Backend розгорнуто на Render, тому перший запит після періоду неактивності може виконуватися довше за наступні.

## Основні можливості

- реєстрація, вхід і вихід користувача;
- збереження авторизації після перезавантаження сторінки через JWT у `httpOnly` cookie;
- серверна нормалізація email: `trim` + приведення до нижнього регістру;
- 6 переговорних кімнат, створених через seed;
- тижнева сітка розкладу з кроком 30 хвилин;
- навігація між попереднім, поточним і наступними тижнями;
- відображення назви бронювання та його автора;
- візуальне розділення власних і чужих бронювань;
- підсвічування поточного дня та поточного часу;
- створення бронювання лише в межах робочого часу офісу щоденно з `09:00–19:00 Europe/Kyiv`;
- серверна перевірка тривалості, часу, меж 30-хвилинних слотів і перетинів;
- зрозуміле повідомлення, якщо вибраний слот уже зайнятий;
- редагування назви власного активного бронювання;
- скасування лише власного майбутнього/активного бронювання з підтвердженням;
- сторінка **My bookings** з окремими секціями поточних/майбутніх і минулих бронювань;
- минулі бронювання завантажуються сторінками по 6 записів;
- перехід із **My bookings** безпосередньо до потрібної кімнати та тижня в розкладі;
- відображення часу у часовому поясі браузера користувача;
- якщо часовий пояс користувача відрізняється від `Europe/Kyiv`, інтерфейс додатково показує офісний часовий пояс;
- стани завантаження, помилки та порожні стани для основних екранів;
- захист login endpoint від багаторазових невдалих спроб входу.

## Вимоги для локального запуску

Перед запуском мають бути встановлені:

- **npm**;
- **PostgreSQL**.

## Локальний запуск

### 1. Клонувати репозиторій

```bash
git clone <repository-url>
cd meeting-room-booking
```

### 2. Створити PostgreSQL базу даних

Створіть локальну базу, наприклад:

```text
meeting_room_booking
```

Це можна зробити через `psql`, pgAdmin або інший PostgreSQL-клієнт.

### 3. Налаштувати backend

Перейдіть у папку backend:

```bash
cd backend
npm install
```

Створіть `.env` на основі `.env.example`:

```env
PORT=4000
CLIENT_URL=http://localhost:3000
DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@localhost:5432/meeting_room_booking?schema=public
JWT_SECRET=replace_with_a_long_random_secret
JWT_EXPIRES_IN=1d
NODE_ENV=development
```

Замініть `YOUR_PASSWORD` на пароль вашого локального користувача PostgreSQL.

Згенеруйте Prisma Client і застосуйте наявні міграції:

```bash
npx prisma generate
npx prisma migrate deploy
```

Застосуйте seed:

```bash
npm run db:seed
```

Запустіть backend у dev-режимі:

```bash
npm run dev
```

Backend буде доступний за адресою:

```text
http://localhost:4000
```

### 4. Налаштувати frontend

У другому терміналі перейдіть у папку frontend:

```bash
cd frontend
npm install
```

Створіть `.env.local` на основі `.env.example`:

```env
NEXT_PUBLIC_API_URL=http://localhost:4000/api
```

Запустіть frontend:

```bash
npm run dev
```

Відкрийте:

```text
http://localhost:3000
```

## Правила бронювання

На backend перевіряються такі правила:

- назва — від 1 до 100 символів після `trim`;
- початок бронювання має бути раніше за кінець;
- початок має бути в майбутньому;
- початок і кінець мають бути кратними 30 хвилинам;
- мінімальна тривалість — 30 хвилин;
- максимальна тривалість — 4 години;
- бронювання має починатися й закінчуватися в один офісний день;
- бронювання має повністю вкладатися в `09:00–19:00 Europe/Kyiv`;
- бронювання однієї кімнати не можуть перетинатися;
- бронювання, що торкаються межами, дозволені: `10:00–11:00` і `11:00–12:00` не конфліктують.

## Перевірка перетину інтервалів

Два часові інтервали вважаються такими, що перетинаються, якщо початок першого знаходиться раніше кінця другого **і** кінець першого знаходиться пізніше початку другого:

```ts
firstStart < secondEnd && firstEnd > secondStart;
```

Та сама умова використовується під час пошуку конфліктного бронювання в PostgreSQL через Prisma. Завдяки строгим порівнянням `<` і `>` суміжні бронювання не конфліктують між собою.

Юніт-тести перевіряють часткові перетини, вкладені інтервали, повний збіг, бронювання впритул, окремі інтервали та сусідні дні.

## Зберігання часу та часові пояси

Час бронювань зберігається в PostgreSQL у полях `TIMESTAMPTZ` і передається між frontend та backend у ISO-форматі UTC. Серверні правила робочого дня перевіряються відносно офісного часового поясу `Europe/Kyiv`.

На frontend часовий пояс користувача визначається браузером. Увесь час у розкладі та в **My bookings** форматується в часовому поясі користувача. Якщо він відрізняється від `Europe/Kyiv`, інтерфейс явно показує інформацію про офісний часовий пояс і відповідний офісний час.

## Захист від одночасного бронювання одного слота

Створення бронювання виконується в Prisma-транзакції з рівнем ізоляції `Serializable`. Усередині транзакції повторно перевіряється наявність конфліктного бронювання перед вставкою нового запису.

Якщо PostgreSQL/Prisma виявляє конфлікт конкурентних транзакцій (`P2034`), операція повторюється до трьох разів. Таким чином, коли два користувачі одночасно намагаються забронювати один і той самий слот, у базі має залишитися лише одне коректне бронювання, а інший запит отримує `409 Conflict`.

## Авторизація та безпека

- паролі хешуються за допомогою `bcrypt`;
- access token створюється як JWT;
- JWT зберігається в `httpOnly` cookie;
- cookie має `secure: true` і `sameSite: "none"` у production;
- захищені маршрути перевіряють авторизацію на backend;
- користувач не може редагувати або скасувати чуже бронювання навіть прямим API-запитом;
- email нормалізується на сервері перед використанням;
- login endpoint має rate limit: 10 невдалих спроб за 15 хвилин, успішні входи не враховуються;
- Express використовує Helmet і CORS із дозволеним frontend origin.


- логіки перетину часових інтервалів;
- серверної валідації часу бронювання.

## Додаткові реалізовані пункти

Окрім базових вимог, реалізовано:

- зрозумілі серверні та клієнтські повідомлення про неможливість створення бронювання;
- скасування власного бронювання із серверною перевіркою власника;
- сторінку **My bookings** з майбутніми та минулими бронюваннями, пагінацією минулих записів і переходом до відповідного тижня розкладу;
- захист від race condition під час одночасного бронювання одного слота через `Serializable` transaction + повторні спроби після `P2034`;
- редагування назви власного активного бронювання;
- rate limiting для невдалих спроб входу.

Повноцінний мобільний сценарій, Docker Compose, email confirmation, recurring bookings, end-of-booking notifications та API integration tests не заявляються як реалізовані бонуси.
